# QuickNotes Data Model Design

## 1. Overview

QuickNotes is a note-taking application where users can create notes, organize them with tags and retrieve their notes when they return to the application.

This design uses a relational SQL database with four entities:

- `users`
- `notes`
- `tags`
- `note_tags`

The database stores structured information, enforces relationships using foreign keys and prevents duplicate emails and duplicate note-tag relationships.

## 2. Entity: Users

The `users` table stores account information for people using QuickNotes.

### Columns

| Column | Type | Constraint | Description |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY | Unique identifier for each user |
| `name` | TEXT | NOT NULL | User's display name |
| `email` | TEXT | NOT NULL, UNIQUE | User's email address |
| `password_hash` | TEXT | NOT NULL | Secure hash of the user's password |
| `created_at` | TEXT | NOT NULL | Date and time the account was created |

The `id` column is the primary key. The `email` column is unique so that two accounts cannot use the same email address.

Passwords must never be stored as plain text. The application should store a suitable password hash generated by a secure password-hashing algorithm.

## 3. Entity: Notes

The `notes` table stores the notes created by users.

### Columns

| Column | Type | Constraint | Description |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY | Unique identifier for each note |
| `user_id` | INTEGER | NOT NULL, FOREIGN KEY | Identifies the note's owner |
| `title` | TEXT | NOT NULL | Note title, limited to 100 characters |
| `body` | TEXT | NOT NULL | Note content; may be an empty string |
| `created_at` | TEXT | NOT NULL | Date and time the note was created |
| `updated_at` | TEXT | NOT NULL | Date and time the note was last updated |

The `id` column uniquely identifies a note.

The `user_id` column references `users.id`. This foreign key connects every note to its owner.

The title must contain between 1 and 100 characters after trimming whitespace. The application should also validate the title before sending it to the database.

The `created_at` value records when the note was created. The application must update `updated_at` whenever the note is modified.

## 4. Entity: Tags

The `tags` table stores labels users can attach to their notes.

### Columns

| Column | Type | Constraint | Description |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY | Unique identifier for each tag |
| `user_id` | INTEGER | NOT NULL, FOREIGN KEY | Identifies the tag's owner |
| `name` | TEXT | NOT NULL | Tag name |
| `created_at` | TEXT | NOT NULL | Date and time the tag was created |

The `user_id` column references `users.id`, so each tag belongs to a user.

A user should not have duplicate tags with the same name. The combination of `user_id` and `name` is therefore unique.

For example, one user can have a tag called `urgent`, while another user can also have a tag called `urgent`.

## 5. Entity: Note Tags

The `note_tags` table connects notes to tags.

### Columns

| Column | Type | Constraint | Description |
|---|---|---|---|
| `note_id` | INTEGER | PRIMARY KEY COMPONENT, FOREIGN KEY | Identifies a note |
| `tag_id` | INTEGER | PRIMARY KEY COMPONENT, FOREIGN KEY | Identifies a tag |

The table uses a composite primary key consisting of `note_id` and `tag_id`.

This means a particular tag cannot be attached to the same note twice.

Both columns are foreign keys. `note_id` references `notes.id`, and `tag_id` references `tags.id`.

## 6. Relationships

### Users to Notes: One-to-Many

One user can create many notes, but each note belongs to one user.

The relationship is implemented using `notes.user_id`, which references `users.id`.

### Users to Tags: One-to-Many

One user can create many tags, but each tag belongs to one user.

The relationship is implemented using `tags.user_id`, which references `users.id`.

### Notes to Tags: Many-to-Many

One note can have several tags, and one tag can be attached to several notes.

This is a many-to-many relationship.

Relational databases represent this relationship using a join table. The `note_tags` table stores pairs of note IDs and tag IDs.

For example, a note with ID 10 could have both the `study` tag and the `urgent` tag. The `note_tags` table would contain two rows for that note.

The join table avoids storing comma-separated tag names in the notes table and makes it easier to search, add and remove tag relationships.

The `note_tags` table resolves the many-to-many relationship between notes and tags.

## 8. CREATE TABLE Statements

The following SQL uses SQLite syntax.

    PRAGMA foreign_keys = ON;

    CREATE TABLE users (
      id INTEGER PRIMARY KEY,
      name TEXT NOT NULL,
      email TEXT NOT NULL UNIQUE,
      password_hash TEXT NOT NULL,
      created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
    );

    CREATE TABLE notes (
      id INTEGER PRIMARY KEY,
      user_id INTEGER NOT NULL,
      title TEXT NOT NULL
        CHECK (length(trim(title)) BETWEEN 1 AND 100),
      body TEXT NOT NULL DEFAULT '',
      created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
      updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
      FOREIGN KEY (user_id)
        REFERENCES users(id)
        ON DELETE CASCADE
    );

    CREATE TABLE tags (
      id INTEGER PRIMARY KEY,
      user_id INTEGER NOT NULL,
      name TEXT NOT NULL,
      created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
      UNIQUE (user_id, name),
      FOREIGN KEY (user_id)
        REFERENCES users(id)
        ON DELETE CASCADE
    );

    CREATE TABLE note_tags (
      note_id INTEGER NOT NULL,
      tag_id INTEGER NOT NULL,
      PRIMARY KEY (note_id, tag_id),
      FOREIGN KEY (note_id)
        REFERENCES notes(id)
        ON DELETE CASCADE,
      FOREIGN KEY (tag_id)
        REFERENCES tags(id)
        ON DELETE CASCADE
    );

These statements create the four tables and enforce the primary keys, foreign keys, required values and uniqueness rules.

The `ON DELETE CASCADE` rule automatically removes a user's notes and tags when that user is deleted. It also removes note-tag relationships when the related note or tag is deleted.

SQLite requires foreign-key enforcement to be enabled for the connection. The `PRAGMA foreign_keys = ON;` statement enables it.

## 9. Example SQL Queries

### Query 1: Retrieve All Notes for a User

This query retrieves the notes belonging to the user with the given email address, newest first.

    SELECT
      notes.id,
      notes.title,
      notes.body,
      notes.created_at
    FROM notes
    JOIN users
      ON users.id = notes.user_id
    WHERE users.email = 'amina@example.com'
    ORDER BY notes.created_at DESC;

The JOIN connects the notes table to the users table through the foreign key. The WHERE clause selects one user's notes.

### Query 2: Find All Notes Tagged "urgent"

This query uses two JOIN operations to connect notes to their tags.

    SELECT DISTINCT
      notes.id,
      notes.title,
      notes.body
    FROM notes
    JOIN note_tags
      ON note_tags.note_id = notes.id
    JOIN tags
      ON tags.id = note_tags.tag_id
    WHERE tags.name = 'urgent';

The first JOIN connects notes to their tag relationships. The second JOIN retrieves the tag names so the query can filter for `urgent`.

The DISTINCT keyword prevents a note from appearing more than once if multiple matching relationships could otherwise produce duplicate rows.

### Query 3: Count Notes for Each User

    SELECT
      users.id,
      users.name,
      COUNT(notes.id) AS note_count
    FROM users
    LEFT JOIN notes
      ON notes.user_id = users.id
    GROUP BY users.id, users.name
    ORDER BY users.name;

The LEFT JOIN ensures that users with zero notes are included. COUNT(notes.id) returns zero for a user without matching notes.

GROUP BY groups the rows by user so the database calculates a separate note count for each user.

### Query 4: Retrieve Tags for a Specific Note

    SELECT
      tags.id,
      tags.name
    FROM tags
    JOIN note_tags
      ON note_tags.tag_id = tags.id
    WHERE note_tags.note_id = 10;

This query lists the tags attached to the note with ID 10.

## 10. Indexes

### Index 1: Notes by User and Creation Time

    CREATE INDEX idx_notes_user_created_at
    ON notes(user_id, created_at DESC);

This index helps the database find a user's notes and retrieve them in newest-first order. That pattern is common when displaying a user's notes in QuickNotes.

### Index 2: Note-Tag Lookup by Tag

    CREATE INDEX idx_note_tags_tag_id
    ON note_tags(tag_id);

The composite primary key on `note_tags` begins with `note_id`, so it is useful for finding tags attached to a particular note.

A separate index on `tag_id` can improve queries that begin with a tag and search for every note associated with it.

Indexes improve suitable reads but require additional storage and can add work to database writes. They should be chosen according to common query patterns.

## 11. SQL or NoSQL?

I would choose SQL for QuickNotes because users, notes and tags have clear relationships, and the application benefits from foreign keys, unique constraints and reliable relational queries.

SQL also supports JOIN operations, which make it straightforward to retrieve a user's notes, find notes by tag and count notes per user. Constraints help prevent invalid relationships and duplicate data.

A NoSQL database could also support a notes application, especially if its data model or scale justified it. However, the structured relationships in this design make a relational SQL database a good fit.

## 12. Data Integrity and Security

The database schema is only one layer of protection. The backend must also:

- Authenticate users before accessing private notes.
- Check that a user owns a note before modifying or deleting it.
- Confirm that a tag belongs to the user before attaching it to one of their notes.
- Use parameterized SQL queries to reduce the risk of SQL injection.
- Hash passwords securely rather than storing plain-text passwords.
- Validate incoming titles and other fields on the server.
- Use transactions when multiple related database changes must succeed or fail together.

These controls help keep QuickNotes data consistent, private and secure.
